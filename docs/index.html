GCP 포트폴리오 데모

Commerce Decision Lab

파편화된 합성 커머스 데이터를 경영 판단의 근거로 바꾸는 시스템. 화려한 대시보드가 아니라, 화면에 뜬 숫자 하나하나를 계산한 SQL까지 거슬러 올라갈 수 있는 추적 가능한 의사결정 시스템을 보여줍니다.

여러 브랜드·채널·유료 마케팅을 운영하는 회사에서, 이번 달 매출이 흔들렸습니다. 원인이 무엇인지 답하는 데 며칠이 걸린다면? 이 데모는 그 질문에 몇 초 만에, 근거를 붙여서 답하는 시스템입니다.

01 · 파편화된 현실

대부분의 조직이 이 상태입니다

주문, 마케팅 지출, 재고, 고객 데이터가 시스템별로 따로 쌓여 있습니다. 이 데모는 실제 회사 데이터 대신, 같은 문제를 재현하도록 설계된 합성 데이터 5종을 씁니다 — 브랜드 3개 × 채널 3개 × SKU 24개 × 고객 900명, 120일 치.

02 · 직접 골라서 끝까지 따라가기

데이터에 4개의 이슈를 실제로 심어뒀습니다

아래 카드 중 하나를 클릭하면, 원본 데이터의 패턴 → 증거 화면 → 시스템이 내린 판단(우선순위·근거·조치)까지, 실제 로컬 실행에서 캡처한 화면으로 끝까지 따라갈 수 있습니다.

1

심어진 패턴

Kestrel 브랜드의 paid_social 채널에서, 최근 30일 구간 지출이 이전 구간 대비 약 2.6배로 늘었지만 기여 매출은 거의 그대로입니다. 다른 브랜드/채널 조합은 지출-매출 관계가 안정적으로 유지됩니다.

2

증거 — Marketing 화면

실제 KPI 테이블에서 Kestrel / paid_social 행만 ROAS가 무너진 게 보입니다.

시스템의 판단 — Decisions 카드

Marlow / retail_partner 세그먼트만 최근 구간 주문 비중이 줄어듭니다. 회사 전체 매출은 대체로 평탄해 보이지만, 이 한 세그먼트에서는 실질적인 순매출 하락이 발생합니다 — 전체 지표만 보면 놓치기 쉬운 패턴입니다.

03 · 대시보드가 아니라 의사결정 시스템

조치 후에도 같은 로직이 다시 확인합니다

"조치가 효과가 있었나?"는 별도 기능이 아닙니다. 이슈를 탐지한 것과 동일한 결정적 함수가 더 최신 데이터에 대해 다시 실행될 뿐입니다. 재고가 회복되면 규칙이 더 이상 발동하지 않고, 이슈는 목록에서 조용히 사라집니다.

예시 — AUR-003 긴급 재입고 시뮬레이션

저장소의 자동화 테스트(tests/test_decisions/test_post_action_verification.py)가 실제로 검증하는 시나리오입니다.

조치 전
days_of_cover = 2.9
on_hand 10 · stockout_risk = True → 이슈 발생
→
긴급 재입고 후
days_of_cover = 34.3
on_hand 120 · stockout_risk = False → 이슈 소멸
같은 detect_inventory_issues() 함수를 두 상태에 각각 실행했을 뿐, 별도의 "검증 로직"은 존재하지 않습니다.
04 · 줌아웃

이걸 움직이는 인프라

모든 컴포넌트는 명확한 이유가 있어서 존재합니다 — 화려함을 위한 게 아닙니다.

flowchart LR subgraph Generate["로컬 / Cloud Run Job (예약 실행)"] Gen[합성 데이터 생성기] end Gen --> GCSraw[("Cloud Storage: raw/날짜/*.csv")] GCSraw --> BQraw[(BigQuery raw)] BQraw --> BQstage[(BigQuery staging)] BQstage --> BQmetrics[(BigQuery metrics)] BQmetrics --> Rules[결정적 이슈 탐지 규칙] Rules --> Gemini[Gemini 해석] Rules --> Snap[app_snapshot.json] Gemini --> Snap Snap --> GCSsnap[("Cloud Storage snapshot")] GCSsnap --> App[Cloud Run Streamlit 앱] Sched[Cloud Scheduler: 매일] -.->|트리거| Gen
Cloud Storage
원본 CSV의 집결지이자, 앱이 읽는 유일한 파일이 있는 곳 — 공개 앱을 BigQuery/Gemini와 완전히 분리합니다.
BigQuery
raw → staging → metrics. 모든 숫자의 결정적 근거(source of truth).
결정 규칙 (Python)
"무엇이 문제인지"는 AI가 아니라 임계값 기반 로직이 정합니다.
Gemini
이미 계산된 이슈를 문장으로 서술만 합니다. 사실이나 심각도를 바꿀 수 없습니다.
Cloud Run + Scheduler
앱 서빙과, 매일 실행되는 전체 리프레시 자동화.

데이터 볼륨은 의도적으로 작고(주문 ~1,600건), Cloud Run은 유휴 시 스케일 투 제로라 실행 비용은 사실상 무료 티어 수준입니다. 임계값과 규칙은 심어놓은 시나리오를 탐지 가능하게 한 데모용 기본값이며 실제 리테일 벤치마크 튜닝은 아닙니다 — 자세한 내용은 저장소 README의 "한계" 섹션 참고.

이게 여러분 조직의 실제 데이터였다면

이 데모는 합성 데이터로 만든 메커니즘 증명입니다. 같은 구조 — 결정적 메트릭, 근거 있는 이슈 탐지, 제한된 역할의 AI 해석 — 를 실제 데이터 소스에 연결하는 건 이미 검증된 패턴을 재사용하는 문제입니다.
